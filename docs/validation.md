# Validation evidence

Validation distinguishes deterministic fixtures, the bounded private live pilot, installation, native discovery and a full portfolio review. This package was not used to perform a complete portfolio audit.

## Behavioral and recovery checks

The local Python standard-library suite covers inventory versus actual assessment/depth, type-specific facets, supported recommendation/prompt fields, unchanged/changed/unknown source versions, duplicate and uncertain associations, rejection/resolution history, saved cursors and continuation mode, limits and partial finish, atomic state corruption detection, and exclusive run ownership. Installation checks cover identical hashes, refusal to overwrite, unrelated-skill preservation, path guards, installed helper execution from another directory, and a competing process rejected during a transaction. Publication fixtures require missing links and missing inventories to fail.

Run `python3 -B -m unittest discover -s tests -v`. The release run and any limitations are recorded below. Fixtures supply deliberate facts and do not establish real project behavior.

## Bounded Phase 1 live observations

The construction pilot inventoried 34 returned project entries, initially assessed three, and reviewed two in depth using selected local materials. Ten inspected source files had matching before/after SHA256 hashes. The third selected project lacked inspected learner feedback and was not counted as reviewed in depth. Native recent-chat and connected search results were metadata only unless an examined boundary was explicitly recorded. Provider searches and partial listings did not establish global account coverage. The private inventory, report, source identities and raw receipts are excluded from the repository.

The private review compared recommendations against examined source sections, checked standalone prompt fields and provisional ranking explanations, and retained the inferred-versus-reproduced distinction. This was a bounded read-only pilot, not a completed portfolio review.

## Package and installation gates

Required gates: Agent Forge `audit --ready`, skill metadata validation, exact root/skill resource inventories, local link validation, intentional failure fixtures, an exact review of staged public contents, user-scope installation with identical hashes, and native `skills/list` readback from directories outside the build. The GitHub readback must establish visibility, source revision/files, MIT license, README and topics.

File installation, native discovery and a model-driven invocation are separate observations. No extra model worker or unbounded review is launched just to demonstrate installation. A successful installed helper command proves only that deterministic helper path; the private live pilot supplies bounded domain-work evidence.

Official host references: [skills and user-level installation](https://learn.chatgpt.com/docs/build-skills), [app-server skill listing](https://learn.chatgpt.com/docs/app-server).

### Independent model evaluation

A separate author constructed original-turn/source fixtures and froze the expected oracle before execution without inspecting the candidate or previous evaluator. Executors received only selected evidence and the skill, never expected labels. The author then independently annotated actual reports and traces against the frozen criteria. Private originals, grading records and failure artifacts remain outside source and installation.

The cases cover absent promised work, code without acceptance, completed work behind stale TODOs, corrections/supersession, rejection, deferral, inaccessible history, ambiguous identity, separate source/install/release drift, repeat-after-completion and narrow versus explicitly comprehensive scope. Three development/repeat audits used one separate executor context; two original held-out audits used fresh native contexts. Development read logs were executor-authored, so they do not independently prove every read or absence of external actions. They are not represented as full native traces.

The initial reports classified requirements correctly but **failed** required impact fields; the initial comprehensive report also omitted a grounded optional-opportunities assessment. Those outputs remain failed. The repair makes the final output checklist apply in every requested scope, requires explicit impact/dependencies for every action, and checks optional opportunities separately from implementation authority.

The corrected comprehensive rerun and a newly authored, previously unseen focused case **passed the unchanged full grading gates**, including scope, authority, source-stage distinctions, action completeness, grounded opportunities and 100% actionable precision/recall and classification accuracy within those small synthetic cases. Both ran in fresh GPT-6 Astra / Extra High native CLI contexts with raw JSONL command traces and unchanged workspace hashes. The comprehensive rerun is regression evidence, not a new held-out case. Minor prose count/wording inconsistencies were retained as observations; these results do not imply universal accuracy or error-free prose.
