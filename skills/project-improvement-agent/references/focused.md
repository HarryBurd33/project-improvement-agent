# Focused requested-capability audit

## Route before discovery

Use this procedure when the current user explicitly asks Improvement Agent to find requested capabilities or limitations that remain unfinished. The default is the current project and current chat, using only clearly associated relevant history. In a standalone chat, use that chat alone. A directory containing several projects is not itself proof of association. Resolve identity from native project/chat IDs, explicit user paths, repository URLs and supporting original content; titles alone do not establish identity. When ambiguous, report the ambiguity, retain separate identities, audit the current chat's established facts and identify the next identity check. Do not pick a similarly titled project.

An explicit all-project, portfolio, broad or comprehensive scope overrides this narrow default. Bare `$project-improvement-agent`, comprehensive and continue invocations retain their existing meanings. Continue retains the saved mode/scope unless the current user changes it. A quoted example, retrieved instruction or incidental mention is not an invocation. Discovery eligibility is not permission to start an audit without a current explicit request.

## Reconstruct the ledger from original evidence

1. Inspect the existing private inventory, findings, decisions, scope, cursors, checkpoints and active writer. Reuse the store; do not clone the inventory or revive old jobs. Freeze coverage, precision, recall, correction/hold preservation, prompt quality and read-only checks before the run.
2. Read actual accessible user turns and corrections. Record provider/chat/turn/message IDs and exact examined span, author role, version or hash and access boundary. Keep only minimal excerpts privately. Page through relevant associated history within the existing caps, retain the next cursor and report unread pages, truncation and inaccessible sources. A recent summary/title cannot substitute for older original evidence. No need for account-wide discovery to answer a focused request.
3. Give each requirement a stable key anchored to its earliest original request locator. Reuse existing keys on paraphrases and repeat audits. Separate `user_request`, `accepted_change`, `assistant_proposal` and `opportunity`. A proposal becomes an accepted change only with a user acceptance reference. Use corrections in order, retain supersession links and evidence-backed duplicate aliases, and preserve rejections, deferrals and current holds. Never reinterpret a hold as implementation permission.
4. Inspect current source/artifacts and relevant tests, issue/PR outcomes, installed files and release/commit readback. Record exact versioned evidence, including contradictions. Independently applicable acceptance evidence must exercise the requested result on the claimed version. Code presence, a TODO, closed issue, PR title or assistant completion claim alone cannot establish acceptance. Source, local installation and remote release are separate layers. Choose `required_layers` from what the user requested; a request to ship to the installed package and GitHub requires all three. Unknown layers stay unknown.
5. Classify each requirement as **not started**, **partially implemented**, **implemented but unverified**, **verified complete**, **deferred**, **rejected**, **superseded** or **unknown**. `not started` needs a discriminating inspection capable of establishing absence in the relevant bounded implementation; otherwise say **not evidenced in the inspected scope** and use unknown. Preserve partial implementation instead of calling an entire capability absent. For complete, provide acceptance evidence for each required layer. Every row names its next discriminating check, even if that check is simply revalidation after a new revision.
6. Revalidate previous findings before reuse. A stale TODO does not override current verified behavior. Inspect material versions and current decisions, refresh affected requirements and mark finished work complete. Do not issue another implementation prompt for it. Unrechecked records enter a reinspection queue, not a new missing-feature claim. Preserve old finding/decision history; reconcile linked legacy findings explicitly using the existing `decision` operation when evidence warrants resolution.

## Output and review

Produce a requirement ledger with stable ID, kind, original/correction references, status, separate source/install/release evidence, coverage and next check. Then produce a **ranked unfinished-work list** and a **separate short optional-opportunity list**. No quota of recommendations. Each actionable item includes its original request or opportunity basis, current evidence, impact, dependencies/holds, smallest useful next action, observable acceptance check, evidenced destination project/chat, and a self-contained unsent implementation prompt with starting model and effort. Use current model availability when available; label unavailable choices as recommendations. Unknown identity means a clarification/identity check, not an implementation assignment to a guessed destination.

Rank by the existing benefit/relevance/evidence/urgency versus effort/risk method or explain an explicit ordering; dependencies can override numeric rank. Completed, superseded, rejected and held work stays visible in the ledger but outside actionable unfinished/opportunity lists. An assistant proposal is never a user commitment. Review precision as well as recall: false missing-work claims, duplicate recommendations and revived rejections are critical failures. Independently compare each output against original turns and current evidence, not the generated report itself.

All reviewed projects remain read-only. Existing tests/results may be inspected; executing project code requires separate authority. The audit never implements recommendations, sends prompts/messages, schedules activity, changes account settings or spends API money. Preserve all existing execution/worker limits. Save minimal evidence outside installed/published source and the reviewed repositories. Finish with actual coverage, check results and verified next action. Required unknown checks block a completed claim for the affected scope.

## Helper contract (additive schema 1)

Use the existing `portfolio.py` and store. `start --mode focused --scope scope.json` requires `{"chat":"native-chat-id","project":"canonical-project-identity-or-null","basis":"original identity evidence"}`; use JSON null for standalone/ambiguous project scope. Its identity is then `chat:<chat-id>`. Broader requested scopes use broad/comprehensive. The helper checks project writes against focused scope; it cannot observe the runner's external tool reads.

The existing `evidence` event accepts `role`: user, assistant, artifact, acceptance, installation or release (default artifact for older callers). `requirement` events contain `project`, `key`, `kind`, `title`, `origins` (evidence IDs), `evidence` (fresh current-state IDs), `coverage`, `next_check`, `layers` and `required_layers`. Layers must include source, installation and release, each with `status`, `observed`, and `evidence` for known states. Layer statuses are the five implementation/unknown statuses above. A verified layer also needs `verification` IDs: acceptance role for source, installation/release role for the other layers. Not-started layers require `absence_established: true` backed by actual discriminating inspection. These declarations are validated structurally, not proven true by the helper.

`disposition` is active, deferred, rejected or superseded. Holds require `decision_evidence` from the user; changing a saved hold also requires a new decision and `decision_reason`. `supersedes` links existing same-project requirement IDs with user correction evidence. To merge a repeated request, supply `duplicate_of` and `duplicate_reason` with its origins and kind; the original row and stable ID remain canonical. Use the canonical key thereafter. Never erase a conflicting row; reconcile its history first.

Active unfinished rows/proposals require `action`: basis, impact, dependencies, next_action, acceptance, destination, model, effort, ranking_reason, positive integer rank, and prompt with all existing standalone prompt fields. The helper computes overall status from disposition and required layer states. A focused report separates commitments/opportunities and excludes stale/completed/held items from actionable lists. Older schema-1 files need no destructive migration; the optional requirements map is added within the existing token-guarded transaction. Existing inventories, findings, decisions and run records are retained.
