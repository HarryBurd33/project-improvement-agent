# Comprehensive review and continuation

Comprehensive mode uses the same private schema and broad-mode findings. It is a manual sequence, never a scheduler. Start each new session with status, prior mode, frozen checks, current authority/resources and exclusive ownership. A previously active run must be reconciled rather than silently reset. Finished runs, source cursors and evidence survive subsequent starts.

Use a fair queue: first reobserve affected/unknown evidence, then finish partially reviewed projects, then review the next inventoried/assessed accessible project. Rotate among types/sources to avoid permanently starving lower-ranked work. Broad mode ranks strongest opportunities; comprehensive mode must eventually consider every discovered project, including low-ranked and no-change projects. Mark inaccessible work blocked with a reason and recovery action; retain it in the report. Reserve discovery calls each session while source queues remain unfinished. Do not repeatedly rescan a capped first page in place of continuing a saved cursor. When no enumeration exists, save the next date/query/root boundary and disclose that coverage is still incomplete.

Before trusting a previous finding, reobserve source versions where supported. Unchanged content hashes/reliable revisions allow reuse of depth work; record current observation. A changed version marks affected reviews `needs_recheck` and findings stale. Revisit affected facets and dependencies; preserve historical evidence. Deleted/unavailable material remains a blocked gap, not a resolved finding. Null/unknown versions require actual reinspection in later sessions; matching timestamps alone do not prove stability. The helper invalidates unknown-version depth at a new start and rejects evidence from a prior unknown-version observation. Do not refresh a finding by relabeling an old read.

An `association` event has `left`, `right` project IDs; `relationship` (`related`/`duplicate`); `certainty` (`uncertain`/`confirmed`); `reason` and an evidence locator/identity. Uncertain links never merge or reduce counts. Confirmed related projects remain distinct. Confirmed duplicates retain stable aliases, source/evidence/decision history and conservatively require reconciliation of their combined evidence. Do not confirm duplicates from titles alone. Native aliases resolve to the canonical project on future events.

A `blocked` event requires project, reason and next_action. After access returns, capture current evidence and assess/review again. Do not delete blocked projects to increase apparent completion.

A `decision` event has finding ID, decision (`rejected`, `resolved`, `accepted`, `deferred`, `proposed`), reason, and current source. Resolved requires fresh verification evidence IDs. Accepted means selected, not implemented. Rejected/resolved findings stay suppressed on repeat ingestion. A finding event may reopen one only when substantive evidence changed and `reopen_reason` explains why; an explicit current user reconsideration can instead set decision `proposed`. Preserve history and explain reopening in the report. New wording alone is not new evidence. Do not infer resolution from silence or disappearance.

Every review must satisfy the PLAYBOOK type facets with actual evidence. Store questions and next_action. The report distinguishes new, changed, unchanged and resolved findings relative to the run's starting baseline, with decisions/staleness separately visible. A revised finding is not proof of an implemented improvement.

Completion is relative to the **discovered, accessible inventory and recorded source/evidence dates**. `depth_complete_for_discovered` is false if any inventoried/blocked/recheck project remains. Even if true, partial/blocked source discovery and uncertain associations remain explicit. There is no percentage of an unknown portfolio, and an empty inventory does not establish completion. Do not claim a current full review until required source observations and depth checks were actually completed under the run contract. A bounded pilot or fixture run is never a portfolio audit.

At a time/action/call/material limit, stop new reads; `finish` still accepts an honest partial report with specific next action and verification. Start a subsequent manual run without resetting the inventory. After a crash, inspect active run, counters, state checksum, source effects and exact owner token. Resume only under current authorization. Do not steal or auto-expire claims, retry uncertain external actions, or restore older decisions from `previous.json` without reconciliation.
